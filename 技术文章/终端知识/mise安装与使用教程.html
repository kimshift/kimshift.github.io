一、为什么要换掉 Volta ​

2025 年 11 月，Volta 官方在 README 和 issue #2080 中正式声明：Volta 已停止维护（unmaintained）。

官方原话大意是：现在能用的功能短期还能继续用，不用急着迁移；但新系统版本或生态变化带来的问题不会再修复，建议把迁移列入维护计划，并推荐迁移到 mise（这也是 Volta 维护者们自己现在在用的工具）。

注意：Volta 并未被归档（archived），只是不再有新功能与修复。所以迁移可以慢慢做，但越早越省事。

二、mise 是什么 ​

mise（读作 /miːz/， "meez"，全称 mise-en-place）是一个用 Rust 写的开发环境管理工具，一个工具同时解决三件事：

能力说明对应 Volta / 其它工具
工具版本管理每个项目目录自动切换 Node / Python / Go / Java 等版本Volta、nvm、asdf
环境变量管理从 mise.toml 或 .env 注入环境变量dotenv、direnv
任务运行用 mise run build 跑项目脚本npm scripts、make、just

和 Volta 的关键差异：

  • Volta 把版本信息写在 package.json 的 volta 字段（必须提交）；mise 用独立的 mise.toml，可以不提交、也可以提交，更灵活。
  • Volta 只管 JS 生态；mise 管几乎所有语言。
  • mise 支持 mise.lock 锁定精确版本，CI 可复现。
  • mise 采用"显式信任"（mise trust）机制：项目配置可能执行代码，第一次进入陌生项目需要确认一次。

三、Windows 安装 ​

3.1 方式一：winget（官方推荐） ​

powershell
winget install jdx.mise

如果卡在 msstore 源的协议确认上，可以只走 winget 源：

powershell
winget install jdx.mise --source winget --accept-source-agreements --accept-package-agreements

3.2 方式二：PowerShell 脚本（无需管理员，装到用户目录） ​

powershell
irm https://mise.run/powershell | iex
  • 安装位置：~\.local\bin\mise.exe（旁边还有 mise-shim.exe），并自动把该目录加入用户 Path。
  • 重复执行即为升级。
  • 可调变量：MISE_VERSION、MISE_INSTALL_PATH、MISE_INSTALL_MODIFY_PATH=0（不改 Path）、MISE_INSTALL_SHIMS_PATH=1（顺带把 shims 目录加进 Path）。

如果你在 Git Bash / MSYS2 里，要这样跑：

bash
powershell.exe -NoProfile -Command "irm https://mise.run/powershell | iex"

3.3 方式三：Scoop / Chocolatey ​

powershell
scoop install mise
# 或
choco install mise

包管理器版本可能落后于官方 release（例如 winget 源里是 2026.10.12，而官网最新是 2026.11.0）。一台机器只用一种安装方式，否则 PATH 里可能留下旧二进制。

3.4 验证安装 ​

powershell
mise --version
mise doctor

mise doctor 会输出配置目录、数据目录、shim 目录、activated 状态等，排查问题时第一条命令就是它。

3.5 Windows 上的限制（重要） ​

mise 原生支持 Windows，但有几个坑必须提前知道：

  • asdf 插件在原生 Windows 上不能用（插件是 shell 脚本）。不过主流工具都走内置后端或 aqua / github / http / npm / vfox，Node 这类完全没问题。用 mise registry <tool> 可以看某工具支持哪些后端。
  • WSL 里要用 Linux 版的 mise，两套分开管理，不要指望 Windows 版的 mise 管 WSL 里的工具。
  • cmd.exe 无法 activate，只能靠 shim。
  • PATH 长度限制 8191 字符，超了 cmd.exe 会直接忽略整个 PATH（详见第十节常见问题 3）。

四、Shell 激活 ​

mise 有三种"让工具生效"的方式，先搞清楚区别：

方式适用场景特点
mise activate交互式终端（PowerShell / Git Bash / zsh）切换目录自动改 PATH 和环境变量；开销在每次提示符
shims编辑器、IDE、cmd.exe、GUI 程序每次调用工具时有微小开销，但不依赖 hook
mise exec -- cmd脚本、CI、临时命令只对这条命令生效，不污染当前 shell

4.1 PowerShell（7+ 推荐） ​

把下面这行加入 $PROFILE（PowerShell 启动时会执行）：

powershell
(&mise activate pwsh) | Out-String | Invoke-Expression

一次性写入 $PROFILE 的脚本：

powershell
if (-not (Test-Path $PROFILE)) { New-Item -ItemType File -Path $PROFILE -Force | Out-Null }
$activation = '(&mise activate pwsh) | Out-String | Invoke-Expression'
if (-not (Select-String -Path $PROFILE -SimpleMatch $activation -Quiet)) {
    Add-Content $PROFILE $activation
}

改完新开一个终端，然后 mise doctor 应显示 activated: yes。

Windows PowerShell 5.1 的坑：5.1 不支持"切换目录即刷新"，只会在下一次提示符刷新，并且启动时会打印一条警告。要么升级到 PowerShell 7，要么设置 $env:MISE_PWSH_CHPWD_WARNING=0 关掉警告。这意味着一行命令里写 cd some-dir; node -v 拿到的仍是上一个目录的版本。

4.2 Git Bash / MSYS2 / Cygwin ​

在对应的启动文件（如 ~/.bashrc）里加一行：

bash
eval "$(mise activate bash)"

注意：mise activate 输出的脚本是按当前运行时生成 PATH 格式的，所以不要在 PowerShell 里生成脚本再拿到 Git Bash 里 source，一定要在目标 shell 自己的启动文件里执行。

4.3 cmd.exe ​

cmd.exe 无法激活，只能走 shims：

powershell
$shims = "$env:LOCALAPPDATA\mise\shims"
$userPath = [Environment]::GetEnvironmentVariable('Path', 'User')
if (($userPath -split ';') -notcontains $shims) {
  [Environment]::SetEnvironmentVariable('Path', "$shims;$userPath", 'User')
}

缺点：shims 只负责找可执行文件，不会把 [env] 里的环境变量注入 shell。

五、快速上手 ​

5.1 不碰配置，先试一下 ​

bash
# 临时用 Node 24 跑一条命令，不安装到当前 shell，也不改任何配置文件
mise exec node@24 -- node --version

5.2 给项目固定版本 ​

bash
mkdir my-project && cd my-project
mise use node@24
# 会安装 Node 24，并生成 mise.toml

生成的 mise.toml：

toml
[tools]
node = "24"

5.3 设置个人全局默认 ​

bash
mise use -g node@24      # 等同于 mise use --global

写到 ~/.config/mise/config.toml（Windows 为 %USERPROFILE%\.config\mise\config.toml）。项目里的 mise.toml 优先级更高。

5.4 加环境变量和任务 ​

bash
mise set NODE_ENV=development
toml
[tools]
node = "24"

[env]
NODE_ENV = "development"

[tasks.build]
description = "构建静态站点"
run = "pnpm build"
bash
mise run build

六、配置文件说明 ​

6.1 文件层级（优先级从低到高） ​

位置用途
/etc/mise（Windows 为 <盘符>\etc\mise）系统级配置
~/.config/mise/config.toml全局配置（mise use -g / mise settings set 写这里）
~/.config/mise/config.override.toml全局覆盖，优先级高于所有项目配置
项目目录及各级父目录的 mise.toml项目配置，越靠近当前目录优先级越高
项目目录的 mise.local.toml个人本地覆盖，不要提交到 Git
.tool-versionsasdf 格式，mise 也能读

常用做法：共享的写 mise.toml 并提交，个人的写 mise.local.toml 并加入 .git/info/exclude。

6.2 信任机制（trust） ​

项目配置能执行代码（[env] 里的 _.source、hook、postinstall 等），所以 mise 只会自动加载"纯版本声明"的配置，其余需要你确认：

bash
mise trust              # 信任当前项目配置
mise trust --show       # 查看各目录的信任状态

mise install / mise exec / mise run 执行时会自动信任当前项目（因为你已经决定运行它的代码）。如果觉得每次确认很烦，可以在全局配置里加：

toml
[settings]
trusted_config_paths = ["~/work"]

6.3 让 mise 读取 .nvmrc / package.json（可选） ​

mise 默认不读 .nvmrc、.node-version、package.json，需要显式开启：

bash
# 全局开启（写到 ~/.config/mise/config.toml）
mise settings add idiomatic_version_file_enable_tools node

# 或只在项目里开启（写到项目 mise.toml）
mise settings add --local idiomatic_version_file_enable_tools node

开启后 mise 会读：

  • .nvmrc（支持 lts/*、lts/iron 这类别名，前面的 v 可省略）
  • .node-version
  • package.json 里的 devEngines.runtime，例如：
    json
    { "devEngines": { "runtime": { "name": "node", "version": "20.20.2" } } }

如果你只想要 .nvmrc、不要 package.json：

bash
mise settings add idiomatic_version_file_disable_files node:package.json

注意：mise 不读 engines.node，因为那是"兼容范围"而不是"开发用版本"。

包管理器同理：开启 idiomatic_version_file_enable_tools = ["pnpm"] 后，mise 会从 package.json 的 packageManager 字段（如 "pnpm@9.1.0"）或 devEngines.packageManager 里取版本，并支持 +sha256.xxx 校验后缀 —— 这实际上替代了 Corepack。

6.4 锁定精确版本（可选） ​

bash
mise lock                # 生成 mise.lock
mise install --locked    # CI 中按 lock 安装

mise use --pin node@lts 会直接把解析出的精确版本写进 mise.toml，适合需要绝对稳定的项目。

七、国内网络加速 ​

7.1 Node 下载走 npmmirror ​

toml
# ~/.config/mise/config.toml
[settings]
node.mirror_url = "https://npmmirror.com/mirrors/node/"

npmmirror 同样提供 SHASUMS256.txt 与 .sig 签名文件，mise 的校验可以正常通过。若某个镜像缺签名导致安装失败，可临时关闭：

toml
[settings]
node.gpg_verify = false

7.2 npm 包源 ​

bash
npm config set registry https://registry.npmmirror.com

mise 的 npm: 后端会读取 npm 自身配置，所以这一步对 mise use -g npm:typescript 这类全局 CLI 同样有效。

7.3 mise 自身的下载 ​

mise 本体和部分后端从 GitHub 拉取，网络差时可以配置 URL 重写（把镜像换成你自己可信的代理）：

toml
[settings.url_replacements]
"https://github.com/" = "https://your-mirror.example.com/github/"

调试用 MISE_LOG_HTTP=1 mise install <tool> 可以看到重写后实际请求的地址。

八、从 Volta 迁移 ​

8.1 命令对照表 ​

Voltamise
volta install node@20mise use -g node@20
volta pin node@20mise use --pin node@20
volta listmise ls / mise ls --current

volta run -- node -vmise exec -- node -v

volta uninstall node@20mise uninstall node@20
package.json 的 volta.node 字段mise.toml 的 [tools] node = "..."（或 .node-version）
VOLTA_HOMEMISE_DATA_DIR（默认 %LOCALAPPDATA%\mise）

8.2 迁移步骤清单（Windows） ​

  1. 安装 mise（见第三节），先不要卸载 Volta，两者可以并存，确认没问题再清理。
  2. 记录当前全局工具：volta list，把 node / pnpm / yarn 版本记下来。
  3. 设置全局默认：mise use -g node@20.19.0（按需替换版本号）。
  4. 打开新终端，mise doctor 确认 activated: yes，node -v 确认版本正确。
  5. 逐个项目迁移：进项目目录执行 mise use node@<版本>，然后删掉 package.json 里的 volta 字段。
  6. 全局 CLI 重新安装为 mise 工具（原来 volta install xxx 装的），例如：
    bash
    mise use -g npm:typescript npm:pnpm
  7. 清理 Volta 残留：
    • 删除用户环境变量 VOLTA_HOME
    • 从系统 Path（以及用户 Path）中移除 Volta 相关的 bin 目录
    • 删除 %LOCALAPPDATA%\Volta（或你自定义的目录）
    • 卸载 Volta（控制面板，或运行安装目录下的 uninstall-volta.ps1）
  8. 重新打开终端，where node / where pnpm 应指向 %LOCALAPPDATA%\mise\...。

之所以要先删 volta 字段再清理环境：Volta 的 package.json 字段只被 Volta 识别，留在那里只是历史包袱；但如果你的 CI 还在用 Volta，先别删。

清理 Volta 残留的 PowerShell 脚本（先看清楚再执行，兼容 Windows PowerShell 5.1）：

powershell
# 1. 删除 VOLTA_HOME 环境变量
[Environment]::SetEnvironmentVariable('VOLTA_HOME', $null, 'User')

# 2. 从用户 Path 中剔除所有带 Volta 的目录，并写回
$userPath = [Environment]::GetEnvironmentVariable('Path', 'User')
$clean = (($userPath -split ';') | Where-Object { $_ -and $_ -notmatch 'Volta' }) -join ';'
[Environment]::SetEnvironmentVariable('Path', $clean, 'User')
$clean    # 打印结果，确认没把需要的目录删掉

系统 Path 需要管理员权限（或用"环境变量"图形界面手动改）。改完后必须重开终端，否则当前会话里还是旧 PATH。

8.3 本机现状（实测） ​

迁移前先看一眼真实情况，别在坏掉的环境上继续叠加工具：

powershell
$env:VOLTA_HOME              # → D:\Program\Volta
Test-Path "D:\Program\Volta"          # → False
Test-Path "D:\Program Files\Volta"    # → False
Get-Command node                       # → 找不到

也就是说：Volta 的安装目录已经被删掉了，但 VOLTA_HOME 和 PATH 里的条目还留着，此时 node / npm 在任何 shell 里都不可用。这种"半卸载"状态最典型的症状就是 node 命令凭空消失，重装 Node 之前先按 8.2 的第 7 步清干净即可。

8.4 以本项目（notebook）为例 ​

原来的 package.json 结尾是：

json
"volta": {
  "node": "20.20.2"
}

迁移后的做法：

  1. 在项目根目录执行：
    bash
    mise use node@20.20.2
    生成 mise.toml：
    toml
    [tools]
node = "20.20.2"
  2. 删除 package.json 中的 volta 字段。
  3. 把 mise.toml 提交到仓库，团队成员（以及 CI）执行 mise install 即可复现环境。
  4. 如果还想让 pnpm 版本也可复现，把它也写进去：
    toml
    [tools]
node = "20.20.2"
pnpm = "9"

实测提示（本机）：VOLTA_HOME 仍指向 D:\Program\Volta，但该目录和 D:\Program Files\Volta 都已不存在，where node 也查不到 —— 说明 Volta 已经"半残"了，环境里的 node 实际不可用。这种情况更适合直接上 mise，而不是先修 Volta。

8.5 CI 怎么处理（重要） ​

本项目 .github/workflows/deploy.yml 目前用的是传统方案：

yaml
- name: Install pnpm
  uses: pnpm/action-setup@v3
  with:
    version: 9

- name: Setup Node
  uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: pnpm

这两个 action 和 mise 不冲突，而且不需要为了迁移 mise 去改 CI。有两条路线可选：

路线 A：CI 保持不动（推荐）

mise.toml 只管本地开发环境，CI 继续用 setup-node。缺点是两个地方要各维护一份版本号，容易漂移。

路线 B：CI 也用 mise

yaml
- name: Install mise
  uses: jdx/mise-action@v5
  with:
    version: 2026.11.0          # 可选：固定 mise 自己版本
    working_directory: .        # 可选：子项目目录

- name: Install dependencies
  run: pnpm install

- name: Build
  run: pnpm build

jdx/mise-action 会自动执行 mise install；仓库里有 mise.lock 时它会自动改用 mise install --locked。它还会把 shim 目录加入 PATH 并把项目 [env] 变量导出给后续步骤，所以后面的 run: 直接写 pnpm build 就行（也可以写成 mise run build）。这样本地和 CI 用同一份 mise.toml，版本只维护一处。

注意：用了这个 action 就可以删掉 setup-node 和 pnpm/action-setup，但要确保 mise.toml 里同时声明了 node 和 pnpm。

想省事还可以用 mise generate github-action --write --task=ci 自动生成工作流文件。

关于 "latest" 的坑 ​

在配置文件里写 node = "latest"，不代表跟着上游自动更新，它的含义是"用我本地已安装的最新版本"。真正拉新版本要用 mise upgrade node 或 mise install node@latest。

同理 node = "20" 会优先复用已安装的 20.x，不会每次自动拿最新的 20.x。

十、常见问题 ​

1. 版本不对 / 工具没生效 ​

按顺序排查：

bash
mise ls --current node      # mise 认为该用哪个版本、来自哪个配置文件
mise which node             # mise 会给哪个可执行文件
mise exec -- node --version # mise 实际跑出来的版本
node --version              # 当前 shell 跑出来的版本
type -a node                # shell 能找到的所有 node（PowerShell 用 Get-Command node -All）

如果 mise exec 对而 node 不对，说明 PATH 里有别的版本管理器在前面，把 mise activate 放到启动文件的最后，并清理 nvm / Volta 的激活行。

2. Config files are not trusted ​

非交互环境（如编辑器扩展、脚本）里 mise 无法弹确认，先在终端里跑一次 mise trust。

3. cmd.exe 报 "不是内部或外部命令" ​

多半是 PATH 超过 8191 字符，cmd.exe 会直接忽略整个 PATH。解决办法：把 MISE_INSTALLS_DIR 指到短路径（如 C:\.mise-installs），或改用 PowerShell。

4. 编辑器/扩展报 spawn EINVAL ​

某些 VS Code 扩展会直接启动 .cmd shim，新版 Node 安全修复后不允许。保持 windows_shim_mode = "exe"（默认），执行 mise reshim 并重启扩展；或把扩展的工具路径指向 %LOCALAPPDATA%\mise\shims 下的 .exe。

5. 新版本明明发布了却装不上 ​

mise 默认有 minimum_release_age = 24h（避免刚发布的版本踩雷）。要立刻装就写精确版本号：

bash
mise use node@24.11.1

6. 怎么升级 mise 本身 ​

用安装它的那个包管理器升级，或：

bash
mise self-update

用 winget 装的建议用 winget upgrade jdx.mise，两种方式混用容易留下两个二进制。
